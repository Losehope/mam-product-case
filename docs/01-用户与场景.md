# 01 · 用户与场景

## 1. 四类角色

这个系统有四类人，他们的目标并不一致，产品设计的第一件事是把「谁为哪一步负责」分开。

### 影迷（C 端浏览者）

- **目标**：知道最近有哪些观影活动、附近有哪些观影团可以加入。
- **触发**：在小程序里刷到项目或团体主页。
- **不需要**：认证、申请、任何管理能力。
- **成功标准**：不用注册也能判断「这个活动跟我有没有关系」。

### 观影团（核心使用者）

- **是谁**：一个城市里组织观影活动的团长，多数是**兼职**，手机是唯一的生产工具。
- **目标**：拿到物料，把活动办成，别在填表上花时间。
- **触发**：渠道方发了新项目；或者活动结束后要交返图。
- **痛点**：
  - 同样的信息（团名、城市、影城、收件地址）每参加一次活动就要填一遍；
  - 一个项目可能要报**多个场次**，场次之间只差时间、影城和数量；
  - 填错了被驳回，不知道错在哪，只能等渠道方在群里说；
  - 发没发货只能问，返图截止时间只能靠记。
- **成功标准**：一次活动从看到项目到提交申请 ≤ 3 分钟。

### 渠道方（供给侧）

- **是谁**：特效厅品牌方、片方、赞助商的投放/市场同学。
- **目标**：把物料精准发给目标团长，控制成本，拿到可复盘的投放证据。
- **触发**：有新片、新厅、新活动要铺。
- **痛点**：
  - 每做一个项目就要重新做一份报名表，字段还不一样（有的要成团证明，有的要网盘链接，有的要多图）；
  - 申请多了只能一条条看、一条条审、一条条填单号；
  - 发出去之后不知道团长有没有真的办活动、办得怎么样。
- **成功标准**：一个 100 单的项目，从审核到发货的总操作时间可控在半小时内。

### 管理员（平台方）

- **是谁**：一个人，兼着运营。
- **目标**：保证进来的人和发出去的项目是真的、合规的。
- **触发**：有新的认证申请、新的项目待审。
- **痛点**：每天要看大量资质材料，无法逐一核实；出问题时要能追溯。
- **成功标准**：认证与项目审核都能在一个列表里处理完，不需要跳页面。

## 2. 核心旅程：团长申领一次物料

```
① 看到项目        小程序 · 项目广场 / 分享链接
       ↓
② 确认资格        已认证观影团？有没有该渠道的准入标签？
       ↓
③ 填申请表        系统预填：团名、城市、默认影城、默认地址
       ↓            多场次可复制，只改时间/影城/数量
④ 提交            进入「待审核」，可修改
       ↓
⑤ 等结果          通过 / 驳回（驳回可改后重提，不用重新填）
       ↓
⑥ 收物料          在「我的申请」看快递公司与单号，一键复制
       ↓
⑦ 活动后返图      按渠道方配置的成果字段上传（合影、多图、网盘链接）
       ↓
⑧ 被评分          渠道方五分制评分 + 评论，进入团体历史评分
```

这条旅程里有三个设计点值得单独说：

1. **③ 预填**：团长维护一次「常用影城」和「常用收货地址」，之后所有申请自动填充，多地址可下拉切换。这是把「重复劳动」变成「一次性配置」。
2. **⑤ 驳回可改重提**：驳回不是终点，申请保留原内容、保留修改入口，重提后回到待审核。否则团长会重新填一遍，错误率更高。
3. **⑦ 返图字段由渠道方配置**：不同项目要的成果不一样，平台不预设死字段。

## 3. 核心旅程：渠道方发一个项目

```
① 建项目        名称、关联影片、报名起止时间、详情（图文）
       ↓
② 配报名表      默认字段可删可改必填，可加自定义字段，可调顺序
       ↓
③ 定可见范围    公开 / 仅准入 / 私密
       ↓
④ 提交审核      草稿 → 待审核（待审核期间不可编辑）
       ↓
⑤ 发布          管理员通过；已发布可再次修改，但名称与影片锁定
       ↓
⑥ 收申请        按项目/状态/观影团/影城/开场时间筛选
       ↓
⑦ 审核          通过（可设备注与通过数量）/ 驳回
       ↓
⑧ 发货          单条填单号，或走批量：导出 → 填写 → 上传 → 预览 → 确认
       ↓
⑨ 返图评分      看返图 → 五分制评分 + 评论 → 申请归档为「已完成」
       ↓
⑩ 看数据        申请总数、各状态分布、明细、字段可选的 XLSX 导出
```

## 4. 场景约束（决定了方案形态）

这些约束不是假设，是业务本身给的：

| 约束 | 对设计的影响 |
|---|---|
| 团长多为兼职，只在手机上操作 | 观影团侧必须做小程序，不做响应式 Web 后台 |
| 渠道方一次处理几十到上百条申请 | 必须有筛选、批量、导出，单条操作不可接受 |
| 物料有成本，超发即损失 | 准入与数量校验必须前置，不能只靠事后审核 |
| 收货信息是敏感数据 | 只对项目所属渠道方与管理员可见 |
| 认证材料含身份证件 | 敏感资源，访问必须鉴权，且要有独立告知 |
| 平台只有一个人运营 | 管理动作必须收敛到少数几个列表页 |
| 活动在影城现场发生，网络一般 | 上传要有超时与重试边界，不能假设 4G 稳定 |

## 5. 明确的非目标

写清楚「不做什么」，比写「做什么」更能说明判断：

- **不做社交**：没有评论、点赞、私信。观影团之间的连接发生在微信群里，系统不抢这个场景。
- **不做支付**：物料由渠道方免费提供，系统不涉及交易。
- **不做全开放的 C 端活动平台**：影迷端只做「看」，不做报名与购票。
- **不做通用表单工具**：报名表是项目的一部分，不是独立产品。
- **不在第一期做 AI 自动评分**：见 [03 关键决策 · ADR-07](03-关键决策.md)。
