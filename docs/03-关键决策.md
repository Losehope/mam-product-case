# 03 · 关键决策

> 每条记录只回答四件事：当时面对什么、有哪些选项、选了什么、付出了什么代价。
> 格式参考 ADR（Architecture Decision Record），但写的是产品决策。

---

## ADR-01 · 准入前置，而不是审核后置

**背景**
原流程里，串发和超发是在申请涌进来之后才被发现的。渠道方要么全收（承担物料损失），要么逐条人工识别（承担时间成本）。

**选项**
1. 公开报名 + 管理员/渠道方人工审核兜底；
2. 公开报名 + 数量与频次限制；
3. 准入前置：渠道标签 + 准入名单 + 邀请码，没有资格的人看不到项目。

**决定**
选 3。渠道方认证即获得唯一标签；观影团通过邀请码或渠道方手动添加获得标签；项目默认对「持标签者」可见。

**代价**
- 失去自然增长：观影团不能自己发现项目，必须被邀请；
- 渠道方多了一步「管理准入名单」的运营动作；
- 邀请码、准入移除与恢复都需要状态一致性设计。

**后来怎么看**
这个交换是对的：物料是有成本的实物，一次超发的损失远大于少来几个团长。但代价也真实存在——**冷启动完全依赖渠道方主动拉人**，所以后来补了「按手机号精确添加」和「批量邀请码」，把渠道方的拉人成本压到最低。

## ADR-02 · 双端分工，不做双端对等

**背景**
最初的设计是「所有角色都能用 Web + 小程序」。做到一半发现，两种用户的任务介质完全不同。

**选项**
1. Web 与小程序功能对等，全量覆盖；
2. 只做 Web；
3. 按任务分工：渠道方/管理员用 Web，影迷/观影团用小程序。

**决定**
选 3。Web 承担建项目、配表单、审核、批量发货、导出；小程序承担浏览、申请、物流、返图。

**代价**
- 两套前端、两套验收，维护成本几乎翻倍；
- 部分能力（如观影团改资料）在小程序上体验受限；
- 登录态、权限、字段口径必须在两端严格对齐，否则会出现「Web 能改、小程序不能改」的割裂。

**后来怎么看**
分工是对的，但**低估了对齐成本**。真正的坑不是写两个界面，而是同一条业务规则在两端各写一遍之后慢慢漂移。如果重来，会先定义一份「字段与状态契约」，两端都对着它实现。

## ADR-03 · 动态报名表 + 档案预填

**背景**
不同渠道方要的信息不一样：有的要成团证明，有的要网盘链接，有的要 3 张现场图。如果写死字段，每接一个新渠道就要改一次代码。

**选项**
1. 固定字段，用备注区兜底；
2. 每个渠道方一套定制表单（硬编码）；
3. 项目级动态字段配置 + 观影团档案预填。

**决定**
选 3。默认字段（城市、团名、影城、时间、数量、收货地址、成团证明）可删、可改必填、可加自定义字段、可排序；字段类型覆盖文本、数字、日期、单选、图片（单图/多图）。

**代价**
- 动态表单让校验、导出、统计都变复杂：每个字段的语义只有配置者知道；
- 已发布项目如果允许改字段，会让历史申请的解释口径不一致，后来收紧为「已发布后名称与影片锁定」；
- 前端需要按配置动态渲染，空状态与异常状态的处理成本显著上升。

**后来怎么看**
动态字段是必须的，但**动态字段 + 动态导出 + 动态统计**是三倍复杂度。第一期只做前两个，统计先固定口径，是正确的收敛。

## ADR-04 · 认证即授权，不自建角色配置台

**背景**
通用后台框架自带完整的角色/菜单/权限配置。理论上可以让运营自己配。

**选项**
1. 开放角色配置台，运营按需配权限；
2. 认证通过后由系统自动授予角色，取消认证自动回收；
3. 硬编码权限判断。

**决定**
选 2。认证是唯一的授权入口，角色与认证状态绑定。

**代价**
- 灵活性下降：无法支持「同一个人同时是渠道方和观影团」之外的复杂组合；
- 认证审核成为单点，管理员不处理就没有新供给；
- 取消认证会立即影响在途业务，需要明确「只限制新增，不中断履约」。

**后来怎么看**
对一个单人运营的平台，**减少可配置项就是减少事故面**。角色配置台看起来很专业，实际上是把这个阶段最稀缺的注意力，花在了最不常变化的维度上。

## ADR-05 · 三档可见范围 + 分享双模式

**背景**
项目并不总是「越多人看到越好」。有的项目要拉新（公开），有的要控量（仅准入），有的只给一两个核心团（私密）。

**选项**
1. 只有公开/私密两档；
2. 公开 / 仅观影团可见 / 私密；
3. 在上述基础上再加「分享直通」。

**决定**
选 3。公开报名、仅准入、私密三档；私密项目不进广场，只能通过带签名的分享链接访问；分享链接分「仍需校验准入」与「直通本项目」两种模式。

**关键约束**
直通**只授权当前项目，不授予渠道标签**，且仍需登录与观影团认证。

**代价**
- 分享凭证需要签名、过期与防篡改，是一块额外的安全面；
- 用户会混淆「我有这个链接」和「我有这个渠道的资格」，需要文案与引导；
- 历史数据（旧的「仅观影团可见」）需要一次性迁移到新模型，且脚本要能重复执行而不覆盖新数据。

**后来怎么看**
分享是这个产品里最像「增长功能」的部分，但它同时是最容易变成「准入后门」的部分。把直通限定在单项目，是这套设计能成立的前提。

## ADR-06 · 批量发货：预览、确认、整批原子

**背景**
一个项目几十上百单，逐条填单号不现实。但批量导入一旦出错，后果不可逆。

**选项**
1. 上传 Excel 直接执行，失败的跳过；
2. 上传后逐条确认；
3. 上传 → 校验 → 预览快照 → 显式确认 → 整批事务。

**决定**
选 3。预览结果保存为一次性快照（10 分钟、绑定账号与项目）；确认时只提交快照凭证；执行前重新校验状态、审核轮次、数量与收件信息；任一变化整批停止；任一环节失败整批回滚。

**代价**
- 实现复杂度高：快照、锁、事务、幂等都要处理；
- 用户体验上多了一步「预览」，有人会觉得麻烦；
- 大数据量下导出与校验都有性能边界（当前限制 5 MB / 5 万条）。

**后来怎么看**
这是整个项目里我最坚持的一条。**「部分成功」在发货场景里等于「没有人知道发了什么」**。多一步确认换来的是可解释、可回滚，值得。

## ADR-07 · AI 评分先做占位，不做假自动化

**背景**
返图审核是渠道方最费时的环节：要看图、判断人数、判断物料是否露出、判断质量。很自然会想到用图像识别自动评分。

**选项**
1. 第一期直接接模型做自动评分；
2. 保留评分入口，但由人打分；
3. 预留字段与接口，明确标注未接入。

**决定**
选 3。评分是人工五分制 + 可选评论；数据结构与接口为后续自动评分预留，但产品上不宣称具备该能力。

**代价**
- 少了一个很漂亮的「AI 功能」卖点；
- 渠道方的审核工作量没有下降。

**后来怎么看**
没有可靠评测集的情况下上自动评分，只会把「渠道方要看的图」变成「渠道方要复核的 AI 结论」，工作量不减反增，还会损伤信任。**在能力边界不清楚时，诚实的占位比虚假的自动化更有价值。**

## ADR-08 · 合规作为上线门槛，不是上线后的补丁

**背景**
系统要收集身份证件、收货地址、手机号，还要在微信生态内运行。这不是「先上线再补」能覆盖的风险。

**选项**
1. 先上线，备案后补；
2. 备案完成后再开放注册；
3. 分阶段：内部与受邀用户可用，公开入口在备案完成后开启。

**决定**
选 3，并把三条独立的合规线拆开管理：**小程序备案、网站 ICP 备案、公安联网备案**。生产页面固定展示备案信息，构建时校验，不提供隐藏开关。

**代价**
- 上线节奏被外部流程卡住，无法按自己的时间表推进；
- 隐私指引必须与真实代码行为逐条对齐（用了哪些权限、收集了哪些信息），改动功能就要同步改文案；
- 身份证件属于敏感个人信息，需要独立告知与同意，不能只靠平台级指引。

**后来怎么看**
合规不是产品的外挂，它直接决定了**哪些功能可以做、以什么顺序做**。把三条备案当成三条独立的关键路径去排期，比把它们混成一句「等备案」要有效得多。
