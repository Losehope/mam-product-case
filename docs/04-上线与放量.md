# 04 · 上线与放量

## 1. 放量策略：用准入系统本身做灰度

这个产品有一个天然优势：**准入机制本身就是灰度开关**。不需要另做一套发布系统，就能控制「谁能进来、能进到哪一步」。

| 阶段 | 范围 | 可见范围 | 退出条件 |
|---|---|---|---|
| **0 · 自用** | 自己 + 1~2 个熟悉的团长 | 私密项目，链接直达 | 主流程无阻断性问题；申请、审核、发货、返图能走完一轮 |
| **1 · 种子渠道** | 2~3 家合作渠道，各自 5~10 个团长 | 仅准入 | 渠道方能在无人指导下独立建项目、审申请、发货；退件与重提可接受 |
| **2 · 分层放开** | 公开项目拉新，准入项目控量，私密项目定向 | 三档并行 | 公开项目不出现明显串发；批量发货无对账问题 |
| **3 · 稳定运行** | 全部合作渠道 | 三档并行 | — |

阶段 1 → 2 的判断依据不是「功能都做完了」，而是**渠道方能不能不问你**。如果每次发货还要打电话确认，说明产品还没准备好。

## 2. 版本节奏

| 版本 | 内容 | 判断依据 |
|---|---|---|
| **v1.0** | 认证、项目、申请、审核、发货、返图评分、Web 管理端 | 先把「一条申请能走完」跑通，宁可少做也不做半条链路 |
| **v1.1** | 渠道准入（标签/邀请码/名单）、项目分享、批量发货、多图表单、小程序登录与物流展示 | 种子渠道跑起来后暴露的真实瓶颈：**拉人太慢**与**发货太慢** |

v1.1 的四项功能没有一项是「原计划里的下一期」，全部来自阶段 1 的实际阻塞。这是我认为这个项目里最健康的一点：**排期跟着摩擦走，不跟着功能清单走。**

## 3. 上线清单

每次发布前固定过一遍，缺一项不上：

**功能**
- [ ] 核心链路（申请 → 审核 → 发货 → 返图 → 评分）在真实角色下走通
- [ ] 权限边界：非归属渠道方看不到别人的项目与申请
- [ ] 敏感资源（认证材料、返图）对无关用户不可访问
- [ ] 空状态、异常状态、网络失败有明确反馈

**数据**
- [ ] 迁移脚本经过演练，可重复执行且不覆盖上线后新数据
- [ ] 迁移前对涉及表做备份，保留恢复路径
- [ ] 生产库业务账号只保留必要权限，DDL 单独走维护流程

**合规**
- [ ] 备案信息在生产页面固定展示，构建时校验
- [ ] 隐私指引与当前实际收集的信息一致
- [ ] 敏感信息（身份证件）有独立告知

**回滚**
- [ ] 保留上一版本可切回
- [ ] 明确「代码回滚」与「数据回滚」是两件事，数据不可直接覆盖

## 4. 发布纪律

三条在项目里被反复验证的原则：

1. **代码发布成功 ≠ 数据库已升级。** 两者必须分别记录、分别验证，不能从「服务起来了」推断「表结构对了」。
2. **小程序有多个状态，不能混为一谈。** 开发版上传、体验版、审核通过、正式发布是四个独立状态。任何一个状态都不能用另一个代替。
3. **对外说「已完成」之前，重新跑一遍与改动范围匹配的验证。** 历史上的通过结果只代表当时。

这三条听起来像工程规范，其实是产品纪律：**它们决定了你对用户承诺的可信度。**

## 5. 观测指标

第一阶段不追求完整的数据看板，只看五个能直接指导动作的数：

| 指标 | 定义 | 用来判断 |
|---|---|---|
| 认证通过率 | 认证通过数 / 提交数 | 准入门槛是不是太高，材料要求是否清晰 |
| 申请通过率 | 审核通过数 / 提交数 | 项目描述与表单是否让人填错 |
| 退件 / 重寄率 | 因地址或信息错误导致的退件数 / 发货数 | 预填与校验是否有效 |
| 返图率 | 提交返图数 / 应返图数 | 履约闭环是否真的闭上 |
| 审核到发货时长 | 申请通过到填写单号的中位时长 | 渠道方的操作成本 |

北极星指标：**有效履约申请数**（已发货且完成返图的申请数）。它同时包含供给、需求和履约，比「注册数」「申请数」更接近业务真实价值。

> 这些指标的定义与取数方式见 [06-数据口径与待补](06-数据口径与待补.md)。没有真实数据之前，不写数字。

## 6. 一个反例：不要用「功能上线」当放量信号

阶段 2 最容易犯的错是：v1.1 做完了，就把所有渠道一次性放进来。结果是新渠道第一次建项目就撞上没覆盖的边界情况，问题集中爆发，而且分不清是产品问题还是运营问题。

放量的正确信号是**存量渠道的摩擦已经降到可接受**，而不是**新功能已经上线**。
