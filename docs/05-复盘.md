# 05 · 复盘

## 做对的

### 1. 先定义一个闭环，而不是先堆功能

v1.0 只做了一件事：让一条申请从提交走到评分。没有活动广场、没有数据看板、没有 AI、没有短信。但这条链路是完整的，所以任何一个真实用户进来，都能走到底。

**可迁移的经验**：判断一个版本是否值得发，不看功能数量，看「有没有一条能被完整走完的路径」。

### 2. 把最贵的错误挡在最前面

串发和超发是实物成本，退件是二次物流成本，错发是不可回收成本。这三类问题都在成本发生之前被拦住了：准入挡在申请前，预填挡在提交前，预览挡在发货前。

**可迁移的经验**：设计时先问「这个环节出现错误，代价是什么、能不能撤回」，再决定在这一步加多少约束。可撤回的环节可以快，不可撤回的环节必须慢。

### 3. 排期跟着摩擦走

v1.1 的四项功能全部来自种子渠道的真实阻塞，没有一项来自我最初的路线图。这避免了「做一个没人用的功能」的典型浪费。

## 做错的 / 付出的代价

### 1. 低估了双端的规则对齐成本

最初以为双端只是「写两遍界面」，实际上最难的是同一条业务规则在两端各实现一次之后慢慢漂移：字段语义、必填校验、状态可见性、错误文案，任何一处不一致都会变成用户投诉。

**如果重来**：在写第一个界面之前，先写一份两端共用的「字段与状态契约」（字段名、类型、必填、可见角色、状态流转），所有实现对着它做。

### 2. 第一期对「公开」的定义含糊

「所有人可见」在实现上其实是「所有登录用户可见」，因为安全框架默认要求登录。这个偏差直到自查时才被发现。

**教训**：产品文案里的「所有人」「公开」必须落到具体的权限判定上，否则它只是一个形容词。

### 3. 已发布项目允许改报名表字段

一开始允许已发布项目继续改字段，看起来灵活，实际上会让历史申请的解释口径不一致——同一个字段，早提交的人填的是旧含义，晚提交的人填的是新含义。

**后来收紧**：已发布后项目名称与关联影片锁定，字段变更需要更严格的前置约束。

### 4. 通知做晚了

站内提醒表在 v1.0 就建了，但通知中心一直没做，导致「申请被驳回」这类关键事件只能靠用户自己回来刷新。

**教训**：状态机里每一个「用户需要知道」的迁移，都对应一个通知需求。通知不是附属功能，是状态机的一部分。

## 没做的（并且明确知道为什么）

| 未做 | 原因 | 如果要做，前提是什么 |
|---|---|---|
| AI 自动评分 | 没有可靠评测集，做了也只是把人工复核换个位置 | 有一批人工标注的返图与评分，能量化准确率与误判代价 |
| 物流轨迹查询 | 只存了快递公司与单号，没有接真实接口 | 明确渠道方是否真的需要轨迹，还是「有单号可查」就够了 |
| 短信验证码 | 微信生态内手机号授权已能覆盖主要场景 | 出现 Web 端大规模注册需求时 |
| 找回密码 / 换绑手机 | 当前账号量小，人工可处理 | 账号量超过人工处理阈值 |
| 完整通知中心 | 已用订阅消息覆盖关键节点 | 站内信成为主要触达渠道时 |

这张表比「已完成功能」更能说明产品判断：**每一条「没做」都有明确的触发条件，而不是「没来得及」。**

## 如果重来，会怎么排

1. **先写规则，再写界面**：对象、状态机、权限矩阵、字段契约四份文档先行，双端都对着它实现。
2. **小程序优先于 Web 精细度**：团长是瓶颈用户，先让他们的路径顺，再优化渠道方的后台效率。
3. **更早接真实用户**：阶段 0 的自用时间可以再短一些，很多问题只有在真实团长手里才会暴露（比如他们根本不会维护「常用影城」）。
4. **通知与状态机同批设计**：每个状态迁移都标注「谁需要知道、通过什么渠道知道」。

---

## 这个项目让我想清楚的三件事

1. **产品设计的核心是约束的位置，不是功能的数量。** 同样的功能，约束放在申请前还是审核后，成本和体验完全不同。
2. **不可逆的动作值得用十倍的成本去设计。** 发货、删除、授权，这三类动作的容错空间是零。
3. **诚实地标注「没做」，比包装「做了」更能建立信任。** 尤其在 AI 功能上，占位就是占位，不能写成能力。
